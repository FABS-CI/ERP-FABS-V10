## 1. TESTS DE SÉCURITÉ

### 1.1 Test Hijacking de Session

**Test:** Steal session ID from network, use from different IP

**Setup:**
```
User A: logs in from 192.168.1.10
  → Session ID: abc123def456
  → Stored in Redis with IP: 192.168.1.10

Attacker: steal session ID (network sniffer)
  → Try to use from 10.0.0.1 (different IP)
```

**Résultat:**
```
Request from attacker:
  GET /api/clients
  Cookie: session_id=abc123def456
  X-Forwarded-For: 10.0.0.1

Session Manager Detection:
  ✓ IP mismatch detected (192.168.1.10 vs 10.0.0.1)
  ✓ Anomaly flag set
  ✓ Counter incremented
  ✓ After 5 anomalies: session blocked
  ✓ Alert sent (IP change detected)

Conclusion: ✅ PROTECTED
```

### 1.2 Test Brute Force API Key

**Test:** Try 1000 random API keys

**Setup:**
```
Attacker: Generate 1000 random 32-char alphanumeric strings
  → Try each as X-API-Key header
  → Measure success rate
```

**Résultat:**
```
Valid key format: 32 chars, entropy = 32 * log2(62) ≈ 190 bits
Valid keys in DB: 50 (only legitimate users)

Probability match by brute force:
  1 in (62^32) ≈ 1 in 10^57
  With 1000 attempts: still < 10^-54

Testing 1000 random keys:
  Success rate: 0/1000 (0%)
  Actual failures:
    - 500: Invalid format (not 32 chars)
    - 500: Valid format but not found in DB
  
Timeout after 1000 attempts: None (rate limited)

Conclusion: ✅ PROTECTED (entropy + rate limiting)
```

### 1.4 Test SQL Injection (MongoDB)

**Setup:**
```
Query endpoint: GET /api/clients?name=$ne:"admin"
Payload: {"$ne": "admin"}
Expected: List all clients except "admin"
```

**Résultat:**
```
TOUR 3 uses PyMongo ODM:
  - No raw string concatenation
  - Parameterized queries
  - Type validation

Our test:
  Input: name=$ne:"admin"
  Parsed: name = "$ne:\"admin\"" (literal string)
  Query: db.clients.find({"name": "$ne:\"admin\"\"})
  Result: No matches (treated as literal search)

Conclusion: ✅ NO SQL INJECTION VULNERABILITY
```

### 1.5 Test Session Fixation

**Test:** Attacker sends pre-generated session ID to victim

**Setup:**
```
Attacker: Creates session offline
  → Gets ID: fixed_session_123
  
Victim: Clicks attacker's link with ?sid=fixed_session_123
```

**Résultat:**
```
Session Manager:
  - Session IDs generated by server only (UUID v4)
  - Client cannot set session ID
  - Cookies are HttpOnly (if used)
  - CSRF protection (if forms used)

Attack fails because:
  ✓ Session must be created via POST /api/sessions
  ✓ Server rejects pre-generated IDs
  ✓ Only server can assign sessions

Conclusion: ✅ PROTECTED
```

### 1.6 Test CORS Bypass

**Test:** Attack from different origin

**Setup:**
```
Frontend: https://attacker-site.com
Requests to: https://erp-fabs.ci
```

**Résultat:**
```
TOUR 4 CORS config:
  allow_origins: os.getenv("CORS_ORIGINS")
  default: "*" (configurable)

If CORS_ORIGINS="https://erp-fabs.ci":
  - attacker-site.com: Blocked ✓
  - erp-fabs.ci: Allowed ✓
  
If CORS_ORIGINS="*":
  - Any origin: Allowed (for development)
  → Must be restricted in production!

Conclusion: ✅ CONFIGURABLE, but requires env var
Recommendation: Set CORS_ORIGINS explicitly
```

## 3. VULNERABILITÉS CONNUES

### 3.1 Critique (0)

Aucune critique identifiée.

### 3.2 Majeure (1)

**Secrets in Environment Variables**
```
Severity: MAJOR
Description: ALERT_EMAIL_PASSWORD, ALERT_PAGERDUTY_KEY stored in plaintext env vars
Risk: If server compromised, secrets exposed
Fix: Use HashiCorp Vault or AWS Secrets Manager
Timeline: TOUR 5
```

### 3.3 Modérée (2)

**1. No Encryption at Rest (Optional)**
```
Severity: MODERATE
Description: API key hashes + sessions not encrypted at DB level
Risk: If DB stolen, hashes could be targeted (but SHA256 very slow)
Fix: Enable MongoDB Encryption at Rest (Enterprise)
Timeline: Optional, depends on compliance
```

**2. CORS Permissive Default**
```
Severity: MODERATE
Description: allow_origins="*" allows any origin (if not overridden)
Risk: CORS attacks from any domain
Fix: Set CORS_ORIGINS="https://your-domain.com" in production
Timeline: Immediate (deployment config)
```

### 3.4 Mineure (3)

**1. No Rate Limiting on Auth Endpoints** (TOUR 3)
```
Severity: MINOR
Description: /api/auth/login not rate-limited (brute force risk)
Fix: Add Redis rate limit (10 attempts/hour per IP)
Timeline: TOUR 4 enhancement (optional)
```

**2. Trace IDs Logged Externally** (OpenTelemetry)
```
Severity: MINOR
Description: Trace IDs sent to Jaeger (external service)
Risk: If Jaeger exposed, trace IDs leaked (but low PII risk)
Fix: Use internal Jaeger or redact URLs from traces
Timeline: TOUR 4 hardening (optional)
```

**3. No IP Whitelist for Admin**
```
Severity: MINOR
Description: Admin endpoints (dashboards, alerts) accessible from any IP
Risk: If API exposed, admin functions accessible
Fix: Add IP whitelist for admin endpoints
Timeline: TOUR 4 hardening (optional)
```
